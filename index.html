Multi-Touch Attribution

GA4 as the touchpoint ledger, with the stitching and modeling in BigQuery

The idea: We use GA4 as the touchpoint ledger and do the stitching and modeling in BigQuery. When a prospect submits a form, the same ID is written to both GA4 and the CRM. BigQuery uses it to match each lead to the visits that came before, so every channel that helped earns credit.

How it works

1Lead formCaptures client ID, session ID, lead key and click IDs
2GA4Every visit plus source, with the lead key as user ID
3CRMLead plus stage dates, with the same keys stored
4BigQueryJoins on the lead key, client ID and click ID
5AttributionCredit by channel for each stage

The four keys that tie it together

KeyWhere it comes fromWhat it does
Lead keyGenerated at form submit. Sent to GA4 as user_id and stored in the CRM.Primary join. Connects later visits across devices.
GA4 client IDGA4 browser cookie.Links the anonymous visits before the form fill.
GA4 session IDGA4 session cookie.Identifies the exact session that converted.
Ad click IDsAd URL parameters (gclid, gbraid, wbraid, fbclid).Fallback join. Enables offline conversion uploads to ad platforms.

Multi-Touch Attribution

Implementation across five systems and the access we need

1

Website and forms

  • Add hidden fields to every lead form: GA4 client ID, GA4 session ID, a unique lead key and ad click IDs (gclid, gbraid, wbraid, fbclid).
  • Add a script that fills those fields at submit. The lead key is generated in the browser at that moment so it reaches the CRM and GA4 together.
  • Every form, including third-party or embedded forms, passes these fields through to the CRM.
2

Google Tag Manager (web and server-side)

  • Push the lead key to the data layer when a form submits successfully.
  • Set it as the GA4 user_id on the Google tag, and store it in a first-party cookie so later visits on that browser carry it.
  • Set a long-lived, server-set visitor cookie through server-side GTM, so returning-visitor tracking isn't cut short by browser cookie limits (Safari limits us to 7 days).
  • If GA4 uses server-managed IDs, read the client ID server-side so the form receives the correct value.
3

GA4

  • Turn on User-ID under Admin, Reporting identity.
  • Link GA4 to BigQuery with the daily export (streaming export if near-real-time reporting is needed).
  • Review key events and confirm Google Ads is linked.
  • Send later CRM stages back to GA4 as events so they also appear in GA4's attribution reports (optional).
4

CRM

  • Create fields for client ID, session ID, lead key and click IDs on the lead record.
  • Keep the first lead key on the record when a person submits again, and keep later keys in a history field.
  • Confirm stage dates are being recorded.
  • Set up a scheduled export or API feed of leads and stages to BigQuery.
5

BigQuery and reporting

  • Build a session table from the GA4 export: visitor, session, timestamp, source, medium, campaign and click IDs.
  • Load CRM leads and stage dates daily.
  • Join the two using the lead key first, then GA4 client ID, then click ID.
  • Build the touchpoint path for each lead and stage within a set lookback window.
  • Apply attribution models (first touch, last touch and data-driven) and report credit by channel for each funnel stage.
  • Report the match rate: the share of CRM leads successfully tied to GA4 data.

Required access

  • GA4 Editor or Admin access
  • GTM Publish access (web and server containers both)
  • Website and form access, or a developer contact who can make the form changes
  • CRM admin, or a CRM contact
  • Google Cloud project with billing account connected
  • List of funnel stages and definitions
We review and confirm the approach against the privacy policy and consent banner before anything goes live.
